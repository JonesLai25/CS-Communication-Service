# 第一章：專案邊界

## 1.1 專案定位

CS 是獨立的 Client–Server 通訊服務。

CS Server 提供服務，CS Client 使用服務。

系統包含：

1. CS Server
2. CS Client
3. 通訊協定與必要函式庫
4. 安裝、更新、解除安裝機制
5. 自動化測試與驗收工具

不包含：

- Job Manager
- Worker Agent
- AI Provider
- 工作排程器
- 分散式運算調度
- Web Taskboard
- 其他尚未被規格要求的功能

CS 可以被上述系統使用，但不能反過來依賴它們。

**通訊是通訊，調度是調度，業務是業務。**

不得因為未來可能整合 Job Manager，就預先加入 Job Manager 專用資料結構或控制流程。

## 1.2 專案獨立性

建立獨立的專案目錄、版本管理、建置流程、測試環境與部署方式。

不得擅自修改現有 Job Manager、SSH 設定、其他專案、既有服務或正式資料。

若現有環境包含可重用工具，應先調查、評估，再決定是否引用。

不允許為了讓新系統運作而破壞已正常運作的舊系統。

# 第二章：工程哲學

## 原則 P01：工作是為了不用工作

軟體的目的不是創造更多操作步驟，而是消除重複勞動。

每設計一項功能，都要問：

- 這個步驟能否自動完成？
- 使用者是否必須介入？
- 能否透過系統狀態自行判斷下一步？
- 發生可預期錯誤時，能否自行恢復？
- 是否讓使用者成為不必要的流程中繼站？

例如檔案傳輸：

使用者只應要求上傳或下載。

OTP 申請、金鑰解封裝、壓縮、加密、分塊傳輸、續傳、完整性驗證、解密與解壓縮，應由軟體自行完成。

正常工作不應要求使用者手動管理中間程序。

**驗收指標：正常流程所需人工介入次數應趨近於零。**

## 原則 P02：事成何必有我

工作的價值在於完成，而不是由誰完成。

人類負責：

- 定義目標。
- 決定授權邊界。
- 提供無法由系統自行取得的資訊。
- 處理真正需要人類判斷的例外。
- 驗收最終成果。

Codex 負責：

- 規劃。
- 實作。
- 測試。
- 分析失敗。
- 在授權範圍內修復。
- 重新驗證。
- 交付結果。

不得把每個可以自行解決的小問題都交還人類。

但自主執行不代表可以自行擴張權限。

**能力、認知與授權是三件不同的事。**

## 原則 P03：哲學名言就是一句了不起的廢話

真正有效的設計原則，在系統完成後應該變成理所當然的行為。

例如：

「斷線可以續傳」不是口號，而是拔掉網路、重新連線後，確實能從已驗證區塊繼續。

「安全隔離」不是口號，而是遠端命令實際無法讀取 Server 私鑰。

「自動恢復」不是口號，而是程序被終止後，系統能判斷哪些工作可以恢復、哪些不能重試。

**每項設計原則都必須對應具體行為、失敗條件與驗收測試。**

無法影響設計決策、無法減少錯誤、無法接受驗證的哲學敘述，不應增加系統複雜度。

## 原則 P04：能動就不要動

對已經正常運作的系統，優先採取最小必要修改。

禁止：

- 無需求依據的大規模重構。
- 為了程式碼美觀改寫已驗證的核心功能。
- 在修復局部問題時順便修改無關模組。
- 在尚未證明替代方案有效前移除舊方案。

修改前必須知道：

1. 為什麼要修改？
2. 預期改善什麼？
3. 可能破壞什麼？
4. 如何證明改善有效？
5. 如何回滾？

新產品開發可以探索，但一旦建立可靠基準，後續變更就必須受到回歸測試約束。

## 原則 P05：先完成核心，再增加能力

不要預先建造未經需求證明的抽象平台。

優先順序：

1. 功能正確。
2. 安全可靠。
3. 故障可恢復。
4. 行為可觀測。
5. 介面穩定。
6. 最後才考慮擴充性與效能優化。

遵循 KISS、YAGNI、低耦合與高內聚。

但簡單不能以犧牲安全、資料完整性或故障恢復為代價。

# 第三章：正確性與驗收哲學

## 原則 P06：執行成功不等於工作成功

必須區分：

- Process Success：程序正常結束。
- Protocol Success：通訊協定正確完成。
- Operation Success：操作結果符合預期。
- Acceptance Success：使用者需求通過驗收。

例如：

Server 回傳 HTTP 200，不代表檔案成功解密。

解密成功，不代表解壓縮後的內容正確。

檔案寫入成功，不代表放在正確的 Workspace。

測試程式回傳 Exit Code 0，不代表整個 CS 系統已通過端到端驗收。

不得將不同層級的成功混為一談。

## 原則 P07：沒有可證偽條件，就沒有完成定義

每項功能在實作前，必須先定義：

- 預期行為。
- 可觀察結果。
- 失敗條件。
- 驗證方法。
- 通過標準。
- 未通過時的診斷證據。

例如：

需求：Server 不得以 root 執行。

驗收：檢查實際 Server 程序 UID，確認非 0。

需求：Client 不能跨使用者下載。

驗收：以 Alice 身分請求 Bob 的檔案，確認拒絕且未洩漏內容。

需求：斷點續傳。

驗收：中斷傳輸，重新連線，比對已驗證區塊與最終檔案 SHA-256。

**凡無法證偽的需求，必須先補足驗收定義，再宣告完成。**

## 原則 P08：做出來、知道錯、修得好、持續改進，是四種能力

不能因為軟體能執行，就認定它具備可靠性。

專案必須建立四個能力層次：

### A. 建構能力

能正確產生要求的功能。

### B. 偵錯能力

能發現實際行為與預期不一致。

### C. 修復能力

能定位原因、修正缺陷、重新測試。

### D. 改進能力

能將已確認的缺陷轉化為回歸測試或設計約束，降低再次發生的機率。

修復完成但沒有驗證，不算完成。

重試成功但不知道先前失敗原因，不得宣稱已根治。

## 原則 P09：未知就是未知

系統必須區分：

- succeeded
- failed
- cancelled
- timeout
- interrupted
- unknown

不得把無法確認的狀態強行歸類為成功或失敗。

例如 Server 執行命令後失去連線，Client 不知道命令是否已完成。

此時不能盲目重新執行，否則可能造成重複副作用。

應優先透過 Request ID 查詢原工作狀態。

**不確定時先取得證據，而不是用重試掩蓋不確定性。**

# 第四章：故障處理哲學

## 原則 P10：故障處理必須形成閉環

標準流程：

工作開始
→ 發現異常
→ 保存證據
→ 分析原因
→ 判斷是否可安全恢復
→ 執行修復
→ 重新驗證
→ 恢復原工作
→ 最終驗收

不得把「錯誤已回報」當成「問題已解決」。

不得把「重新啟動成功」當成「原工作已完成」。

如果無法自行恢復，應提供足以讓人類判斷的診斷資訊，而不是只回傳模糊的失敗訊息。

## 原則 P11：自動恢復必須受到安全邊界約束

允許自動恢復的前提：

- 操作可證明具有冪等性，或能確認原操作尚未產生副作用。
- 不需要提高權限。
- 不會破壞已完成的資料。
- 有明確的重試次數與停止條件。
- 能保留原始失敗證據。

不允許為了讓測試通過而：

- 關閉 TLS 驗證。
- 放寬檔案權限。
- 關閉沙箱。
- 忽略加密驗證錯誤。
- 刪除失敗紀錄。
- 無限制重試。
- 擅自使用 sudo。

安全機制失效時，應拒絕操作，而不是自動降級。

## 原則 P12：錯誤必須留下可利用的證據

每次失敗至少應能追查：

- 發生時間。
- Request ID 或 Transfer ID。
- 操作階段。
- 錯誤分類。
- 預期結果與實際結果。
- 必要的環境資訊。
- 已採取的恢復措施。
- 最終狀態。

日誌不得包含明文 OTP、私鑰或其他機密資料。

觀測機制是為了降低故障分析成本，不是為了累積大量沒有用途的紀錄。

# 第五章：架構設計原則

## 原則 P13：責任分離

每個模組應有明確責任。

建議邏輯模組：

- Identity / Enrollment
- Authentication / Authorization
- Transfer Key Management
- File Transfer
- Command Execution
- Sandbox
- Session / Request Tracking
- Persistence / Recovery
- Installation / Service Management

這是邏輯責任劃分，不代表必須拆成多個服務或程序。

優先採用簡單的模組化單體架構。

不得為了展示微服務架構而增加網路跳點、部署負擔或故障來源。

## 原則 P14：機制與策略分離

通訊層只負責可靠傳送與回應。

認證層負責確認身分。

授權層負責判斷能否執行操作。

檔案層負責加密封裝、傳輸、驗證及提交。

命令層負責執行與回報程序結果。

上層應用自行判斷業務目標是否完成。

CS 不應理解 Python、TTS、AI 推論或其他應用的業務意義。

## 原則 P15：預設最小權限

sudo 僅限需要系統管理權限的安裝與維護操作。

正常 Server 執行、OTP 管理、檔案傳輸與遠端命令，不得以 root 身分執行。

必須區分：

- Linux 系統管理員。
- CS 系統管理員。
- CS 一般使用者。
- 已註冊 Client 裝置。
- 個別操作的授權。

通過身分認證，不代表取得所有操作權限。

## 原則 P16：安全與可靠性不能依賴假設

不要假設：

- 使用者一定會正確操作。
- 網路一定穩定。
- Server 不會重啟。
- 檔案不會損毀。
- 磁碟一定有空間。
- 解壓縮內容一定安全。
- 測試環境與正式環境相同。

應使用明確的狀態機、完整性驗證、權限檢查、資源限制與持久化恢復機制。

任何安全性主張都必須有對應的測試證據。

# 第六章：Codex 自主工作規範

## 6.1 啟動前調查

先檢查：

1. 作業系統與版本。
2. 編譯器、執行環境與依賴。
3. 現有工作目錄與權限。
4. 可用的沙箱機制。
5. 可用的加密與壓縮函式庫。
6. 可用的測試工具。
7. 安裝與部署限制。

不得臆造已安裝的工具、存在的 API 或已取得的權限。

## 6.2 先設計，再實作

首先產出：

- ARCHITECTURE.md
- SECURITY_MODEL.md
- PROTOCOL_DESIGN.md
- STATE_MACHINE.md
- FILE_TRANSFER_DESIGN.md
- INSTALLATION_DESIGN.md
- TEST_PLAN.md
- ACCEPTANCE_MATRIX.md
- IMPLEMENTATION_PLAN.md
- RISK_REGISTER.md

每份文件都應回答實際工程問題，避免重複規格內容。

對於尚未確定的技術選擇，提出候選方案、取捨理由與驗證方法。

不得將未驗證的假設寫成既成事實。

## 6.3 分階段實作

建議階段：

**Phase 0：環境盤點與架構設計**

確認技術選型、安全邊界與可驗收性。

**Phase 1：Server / Client 基礎通訊**

建立 TLS、Request ID、身分驗證與基本請求回應。

**Phase 2：使用者與 Enrollment OTP**

完成使用者建立、公鑰註冊、撤銷及權限驗證。

**Phase 3：Transfer OTP 與檔案傳輸**

完成 Server 核發傳輸密鑰、加密壓縮封裝、上傳與下載。

**Phase 4：續傳與持久化恢復**

完成區塊驗證、斷點續傳、程序重啟恢復與異常清理。

**Phase 5：命令執行與安全沙箱**

完成受限命令執行、結果回收、逾時與取消。

**Phase 6：安裝與系統服務**

完成 User Mode、System Service Mode、Linux / Windows Client 安裝與升級。

**Phase 7：端到端測試與正式驗收**

完成跨平台、故障注入、安全測試與安裝驗證。

階段可以依實際依賴調整，但不得跳過必要的安全驗證。

## 6.4 每階段必須交付

- 實際完成的程式碼。
- 可重現的建置方式。
- 自動化測試。
- 測試輸出與證據。
- 已知限制。
- 未完成項目。
- 回滾方式。
- 下一階段的進入條件。

不得只交付文字說明就宣稱實作完成。

## 6.5 自主決策與求援界線

在已授權範圍內，Codex 應自行：

- 排查一般建置錯誤。
- 修復程式缺陷。
- 補充必要測試。
- 分析失敗日誌。
- 重新執行可安全重試的測試。
- 更新設計文件。

遇到以下情況應停止相關操作並請求確認：

- 需要新增系統管理權限。
- 需要修改既有正式服務。
- 需要刪除或覆蓋不可恢復資料。
- 規格存在互相矛盾的要求。
- 安全要求與功能需求無法同時成立。
- 需要改變已核准的專案範圍。

其他不影響授權、安全與需求的工程細節，應自行做出合理決策並記錄。

# 第七章：品質門檻

## 7.1 測試分層

至少包含：

1. Unit Test
2. Integration Test
3. Protocol Compatibility Test
4. Security Test
5. Fault Injection Test
6. Recovery Test
7. End-to-End Test
8. Installation / Upgrade / Uninstall Test

Mock 測試可以驗證局部邏輯，但不能取代真實 Server–Client 通訊驗收。

## 7.2 驗收結果分級

每個驗收項目只能使用：

- PASS：實際測試通過，具備證據。
- FAIL：測試失敗，保留原因。
- UNVERIFIED：尚未測試或環境不具備。
- BLOCKED：存在明確阻礙，無法執行。

不得將 UNVERIFIED 視為 PASS。

不得將設計完成視為功能完成。

不得將單元測試通過視為跨平台驗收完成。

## 7.3 完成定義

功能只有在以下條件同時成立時，才可以宣告完成：

- 符合規格。
- 正常路徑測試通過。
- 重要失敗路徑測試通過。
- 安全邊界未遭破壞。
- 可以重現測試結果。
- 有明確的驗收證據。
- 未留下未揭露的重大風險。

若尚有未完成條件，必須如實標記。

# 第八章：專案治理

## 8.1 單一事實來源

規格書是功能需求來源。

工程設計文件是實作決策來源。

測試結果是完成狀態的證據來源。

三者發生矛盾時，必須指出矛盾並處理，不得自行假裝一致。

## 8.2 變更控制

每次重要變更記錄：

- 變更原因。
- 影響範圍。
- 修改內容。
- 測試結果。
- 相容性影響。
- 回滾方法。

不要求形式繁複的審批流程，但必須保留可追溯性。

## 8.3 不創造無效工作

避免：

- 重複文件。
- 沒有使用者的抽象介面。
- 沒有需求的設定選項。
- 不必要的背景程序。
- 不能改善診斷的日誌。
- 無法證明價值的重構。
- 只為展示架構而建立的模組。

每增加一層複雜度，都應能說明它解決什麼已知問題。

# 第九章：立即執行指令

收到本文件及 CS v0.1 規格書後，請依序執行：

**第一步：建立專案工作區**

確認目前目錄，建立獨立 CS 專案及版本管理結構。

不得修改其他專案。

**第二步：進行環境盤點**

調查可用工具、系統能力及權限限制。

**第三步：需求一致性檢查**

檢查 CS 規格是否存在矛盾、遺漏、安全風險或不可驗收的敘述。

特別檢查：

- Enrollment OTP 與 Transfer OTP 的區別。
- Server 核發傳輸密鑰的安全性。
- 加密壓縮與斷點續傳的相容性。
- OTP 過期與重啟恢復。
- Non-root 沙箱可行性。
- 多使用者工作區隔離。
- Windows / Linux 相容性。
- 安裝權限與執行權限分離。

**第四步：提出架構與技術選型**

選擇可維護、可測試、依賴合理的方案。

優先使用成熟的密碼學與系統函式庫，不自行發明加密演算法。

**第五步：建立可證偽驗收矩陣**

每個需求都應對應至少一項測試。

重要安全要求必須包含反向測試。

**第六步：制定實作順序**

識別依賴、風險與里程碑。

優先完成最小可運作的 Server–Client 垂直切片，再逐步擴充。

**第七步：開始受控實作**

在授權範圍內持續執行、測試、修復與驗證。

遇到阻礙時先自行分析，只有需要人類授權或規格決策時才請求協助。

# 最終工程目標

「工作是為了不用工作。」

「事成何必有我。」

「哲學名言就是一句了不起的廢話。」

這三句話不是裝飾性的專案標語，而是工程決策標準。

當 CS 完成後：

使用者不需要理解 OTP 如何交換，就能安全傳輸檔案。

使用者不需要管理傳輸區塊，就能在斷線後續傳。

使用者不需要反覆檢查程序，就能取得正確的執行結果。

系統發生錯誤時，不會假裝成功。

系統無法確定狀態時，不會盲目重試。

系統需要人類協助時，能明確說明原因與證據。

**一套真正成功的系統，應該讓正常工作變得理所當然，讓異常有跡可循，讓人類只需要處理真正值得人類處理的問題。**

請開始建立 CS Communication Service 專案。

第一階段先完成環境盤點、規格一致性審查、架構設計及驗收矩陣。完成後，若不存在需要人類決策的重大阻礙，即可依階段計畫進入實作；不得擅自部署到正式環境或修改既有服務。

## 我另外補上的三個關鍵約束

這三個約束是根據你先前在 Job Manager、Codex 自動化與配音驗收時遇到的問題，特別放進去的。

**第一，將「完成工作」與「證明完成」拆開。** Codex 不能再以建置成功、Exit Code 0 或 Mock 測試通過，就認定需求已完成。這直接對應你強調的「做出來、察覺錯誤、修正、改進」四個不同能力。

**第二，自主權不能等於無限授權。** Codex 可以自行除錯、修復與重新驗證，但不能為了通過測試擅自關閉安全機制、提高權限或修改現有系統。

**第三，失敗後要恢復原工作，而不是只修好故障。** 例如傳輸到 60% 時中斷，真正的完成不是把連線修好，而是恢復傳輸、驗證整包內容、成功解封裝並回報原始請求者。

這份啟動指令的作用，是讓 Codex 從一開始就把**可證偽性、故障閉環、最小權限、責任分離和減少人工介入**當成架構約束，而不是等功能寫完才補救。
